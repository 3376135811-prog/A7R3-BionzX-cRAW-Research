# Sony α7R III (`ILCE-7RM3`) v3.10 离线逆向闭环报告：`0x1e` 消息源、`VBB RX` 像素格式与 `AVC 0x99c74` 全链路核验

> **核心结论（一句话版）**
> 1. **消息与参数闭环已 100% 接通**：`av-cam.bin` 唯一通过 `0x41ba4c → 0x4235d0 → 0x40aa70 → 0x426740` 构造并发出 IPC 命令 `0x1e`（`msg+0x0c = A`，`msg+0x10 = B`）；`vcd_firmware.bin` 收到后，**同一份 `B` 数据块同时驱动 `VBB +4`（写寄存器 `0xbf075100`）和 `cmd_adaptor_venc`（`0xeef54`/`0xeef5c` → 内部消息 `0x8342` → `0x1b8d4` → `0x6fef0` → `0x13b48` → `AVC 0x99c74 → 0x9c2e0`）**，完美闭环生成 `110/2/2`（High 10）或 `122/2/2`（High 4:2:2）。
> 2. **像素低两位（真 10-bit vs 伪 10-bit）已由两套固件交叉定性**：`VBB +4`（`0xbf075100`）仅代表 **VBB 送往编码核的目标像素格式**（`0..3`），而 **VBB 从 DRAM 读取源帧的真实内存布局与位深由 `A[0x48]`（官方字段名 `InputFormat` → `VBB +0` → `0xbf075110`）决定**。`vcd_firmware.bin` 的 `vbb_drv.cxx`（`0xe074` 跳表 `0x1714d8`）与 `av-cam.bin` 的 `create_imola_enc_start_param`（`0x41bb04`–`0x41bc06`）一致证明：仅当 `A[0x48] ∈ {1, 2, 5}`（及微码保留项 `7`）时 DRAM 输入才是 **10-bit**；而在原厂 A7R3 管线（乃至仅修改 `B` 表项的补丁）下，上游 `SyncYCOut`（`+0x2f` 钳位在 `0/1`、`+0x36 = 0`）与 `CODEC V`（`0xb5a0a` 硬编码 `chroma = 0`）**强制令 `A[0x48]` 只能取 `3`（8-bit 压缩）或 `6`（8-bit 未压缩 4:2:0）**——即 DRAM 源像素只有高 8 位，低 2 位在进编码器前并不存在。

## 二、接手点一：谁构造并发出 `0x1e` 消息？`A` 和 `B` 的官方定义是什么？

在 `av-cam.bin`（`static-view.o`）中检索 IPC 报文头发包函数 `0x783c82` 的全部 13 处调用点后，确认 **命令 `0x1e` 全固件只有唯一一条发送链**（单点调用、无旁路）：

| 阶段 | `av-cam.bin` 地址 | 源文件名（固件内置日志字符串） | 精确行为 |
|---|---|---|---|
| 1. 组装参数块 | `0x41ba4c` | `enc/imola_enc_param.cpp` (`create_imola_enc_start_param`) | 在栈上构造 `0x588` 字节启动结构体 `r4`：`r4+0x08`（`0x80` 字节）为 **块 A**，`r4+0x88`（`0x1c0` 字节）为 **块 B**，`r4+0x248`（`0x40` 字节）为块 C，`r4+0x288`（`0x300` 字节）为块 D。 |
| 2. 状态机触发 | `0x4235d0` | `enc/imola_enc_state.cpp` | 在 `0x42357a` 调 `0x41ba4c` 生成结构体后，于 `0x4235d0` 唯一调用 `0x40aa70`。 |
| 3. OPA 缓冲拷贝与字段日志 | `0x40aa70` | `common/imola_common_api_enc_handler.cpp` (`[ENCHANDLER]`) | `0x40aab8` 将 **块 A**（`0x80` 字节）拷入 OPA 共享内存 `[sp+0x98]`；`0x40ab44` 将 **块 B**（`0x1c0` 字节）拷入 `[sp+0x90]`；`0x40b200`–`0x40d100` 逐字段打印官方名称；`0x40d126` 唯一调用 `0x426740`。 |
| 4. 物理地址转换与发送 `0x1e` | `0x426740` | IPC 发送层 | `0x4267b8: movs r1, #0x1e; bl 0x783c82` 填写命令号 `0x1e`；经 `0x63475c` 转物理地址后，在 `0x4267f4` 将 **A** 写入 `msg+0x0c`（`P+0x08`），在 `0x42680c` 将 **B** 写入 `msg+0x10`（`P+0x0c`），调 `0x427234` 投递给 `vcd_firmware.bin`。 |

### `[ENCHANDLER]` 日志还原的 `A` / `B` 关键字段真名
由 `0x40b300`–`0x40bd70` 格式化输出直接确认（零猜测）：
- **块 A（输入源与通道公共配置，`0x80` 字节）**：
  - `A[0x00]`：`PicFormat`
  - `A[0x0c..0x13]`：`InputHorizontalSize` / `InputVerticalSize`
  - **`A[0x48]`（即 `r4 + 0x50`，`0x41bb4a: strb.w r3, [r4, #0x50]`）：`InputFormat`**
  - `A[0x49]`（`r4 + 0x51`）：`OutputFormat`
- **块 B（编码流配置 `StreamConf`，`0x1c0` 字节）**：
  - **`B[0x00]`（`r4 + 0x88`）：`CodecType`**（`1` = H.264/AVC，`2` = H.265/HEVC；与 `vcd_firmware.bin` 断言字符串 `(1) == enc_conf.StreamConf.CodecType` / `(2) == enc_conf.StreamConf.CodecType` 完全一致）。
  - **当 `CodecType == 1`（AVC，`0x41bd72`–`0x41bdf8` 从 `0x85eed0` `config_start_param_avc` 表拷贝）**：
    - `B[0x17]` = `Profile`（`100` High / `110` High 10 / `122` High 4:2:2）
    - `B[0x18]` = `Level`
    - **`B[0x19]` = `ChromaFormat`**（`1` = 4:2:0，`2` = 4:2:2）
    - **`B[0x1a]` = `BitDepth`**（`0` = 8-bit，`1` = 10-bit）
  - **当 `CodecType == 2`（HEVC，`0x41bfec`–`0x41c030` 填写，多出 `TierFlag` 字段故偏移前移）**：
    - `B[0x13]` = `Profile`，`B[0x14]` = `Level`，`B[0x15]` = `TierFlag`，**`B[0x16]` = `ChromaFormat`**，**`B[0x17]` = `BitDepth`**。

## 三、接手点二：`vcd_firmware.bin` 中谁读取 `0xeef54`/`0xeef5c` 与 `0xee7f0`/`0xee800`？如何连到 `0x99c74`？

此前追到 `cmd_adaptor_venc.cxx`（`0xee244`）保存转换后的色度与位深字节后断开；现已将中间经过的一次内部消息投递与两次结构体拷贝逐指令完全闭合：

### 1. 写入点核对（`cmd_adaptor_venc.cxx`）
通道配置临时区位于 `s1 = (base + ch * 0xcc) + 4`（共 `0x80` 字节）：
- **类型 1（AVC，`0xeedc4`）**：
  - `s1 + 0x15` = `0`（帧编码 AVC 内部标识；场/MVC 时为 `3`）
  - `s1 + 0x2c` = `B[0x17]` (`Profile`)，`s1 + 0x2d` = `B[0x18]` (`Level`)，`s1 + 0x2e` = `WidthMB - 1`，`s1 + 0x2f` = `HeightMB - 1`
  - **`0xeef54`** (`a2220030: sb v0, 0x30(s1)`)：**`s1 + 0x30 = H(B[0x19])`**（`B[0x19]=1`→`0`，`B[0x19]=2`→`1`）
  - **`0xeef5c`** (`a23e0031: sb s8, 0x31(s1)`)：**`s1 + 0x31 = (B[0x1a] != 0)`**（`0` 或 `1`；注：`0xeef58` 为夹在中间的 `addu a0, s6, zero`）。
- **类型 2（HEVC，`0xee664`）**：
  - `0xee770` (`sb s4, 0x15(s2)`)：`s2 + 0x15 = 2`（HEVC 内部标识）
  - `s2 + 0x2c..0x33` = `Profile`, `Level`, `TierFlag`, `WidthMB - 1` (u16), `HeightMB - 1` (u16)
  - **`0xee7f0`** (`a2420034: sb v0, 0x34(s2)`)：**`s2 + 0x34 = H(B[0x16])`**
  - **`0xee800`** (`a2420035: sb v0, 0x35(s2)`)：**`s2 + 0x35 = (B[0x17] != 0)`**。

### 2. 内部消息 `0x8342` 投递与接收（`0xedbb0` → `0x1fbd4` → `0x1b8d4`）
1. **发包（`0xee348: jal 0x800edbb0`）**：
   `0xedbf0`–`0xedc04` 取同一块地址 `s0 = (a0 + ch * 0xcc) + 4`，以消息号 **`0x8342`**、载荷长度 `0x80` 调 `0x12c4e0`（`MsgPacket` 队列）发往编码控制任务。
2. **收包分发（`0x1fbd4` → `0x1b8d4`，`gop_mng.cxx`）**：
   `0x1fbd4` 匹配消息号 `0x8342`，通过状态对象虚表 `+0x10`（`0x196374` 中指向 **`0x1b8d4`**）处理该包。`0x1b950` 令 `s2 = msg + 8`（即 `0xedbb0` 发出的 `0x80` 字节载荷本体），随后 `0x1b984` 读取 `s2 + 0x15` 分流：
   - **AVC 分支（`s2 + 0x15 == 0`）**：`0x1b9d0` 调 `0x6fe78` 创建 AVC GOP 控制对象（虚表 `0x80198fc8` / `0x8019904c`），并在 `0x1ba18` 调其虚表 `+0x0c` 即 **`0x6fef0`**。
     - 在 `0x6fef0`（`0x6ff00`–`0x6ff44`）中：`a2 = s2 + 0x2c`，`a3 = gop_obj + 0x70`，将 `s2 + 0x2c .. 0x93` 原样拷入 `gop_obj + 0x70`！
     - 因此：**`s1 + 0x2c` (`Profile`) → `gop_obj + 0x70`**，**`s1 + 0x30` (`0xeef54`) → `gop_obj + 0x74`**，**`s1 + 0x31` (`0xeef5c`) → `gop_obj + 0x75`**。
   - **HEVC 分支（`s2 + 0x15 == 2`）**：`0x1bc24`/`0x1bc60` 创建 HEVC GOP 控制对象（虚表 `0x8019828c`），调虚表 `+0x0c`（`0x5acc4 → 0x5a2bc`），同样把 `s2 + 0x2c .. 0x97` 拷入 `gop_obj + 0x70`（故 `0xee7f0`/`0xee800` 落入 `gop_obj + 0x78` / `+0x79`）。

### 3. 装填共享参数块并送达 `AVC 0x99c74`（及 `HEVC 0x66c74`）
1. **拷入帧级共享缓冲（`0x126b0: jal 0x80013b48`）**：
   在 `0x13ba0` 取 `s7 = gop_obj + 0x70`，于 `0x13c7c`–`0x13cc4` 将这 `0x6c` 字节原样复制到 **`[0x188(s3)]->buf + 0x14`**，并在 `0x13cd4` 将 `0x184(s3)` 的 **bit 0 置 `1`**（标记序列参数已更新）。
2. **终点汇合**：
   - **AVC 终点（`0x7d7e4 → 0x9938c → 0x999f0 → 0x99c74`）**：
     `0x9944c` 检测 `0x184(s3)` bit 0 为 `1` 后进入 **`0x99c74`**，此时 `s0 = [0x188(s3)]->buf + 0x14`：
     - `0x0(s0)` = `Profile`（`0x99d1c`/`0x99d28`/`0x99d44`/`0x99d50` 依次放行 `100`、`110`、`122`、`244`）
     - `0x4(s0)` = **`s1 + 0x30`（来自 `0xeef54`）** → 作为 `a1` 传给 **`0x9c2e0`**
     - `0x5(s0)` = **`s1 + 0x31`（来自 `0xeef5c`）** → 作为 `a2` 传给 **`0x9c2e0`**
     - 当 `B` 传入 `Profile=110, ChromaFormat=2, BitDepth=1` 时，`0x9c2e0` 精确产出 **`110/2/2`**；传入 `Profile=122, ChromaFormat=2, BitDepth=1`（对应 `av-cam.bin` `0x85eed0` 第 `43..65` 行表项）时，精确产出 **`122/2/2`**（High 4:2:2 10-bit）！
   - **HEVC 终点（`0x677c0 → 0x66c74`）**：
     `0x677cc` 检测 `0x184(s2)` bit 0 后调 `0x66c74`，在 `0x66ce4`（`lbu v1, 0x8(a1)`）和 `0x66cec`（`lbu v0, 0x9(a1)`）精确消费 `0xee7f0` 与 `0xee800` 保存的字节。

> **阶段定论**：只要命令 `0x1e` 走 `0xdf8d0` 路由值 `0x0c`（编码启动标准路径），**`VBB +4`（`0xbf075100`）与 `AVC 0x99c74` 百分之百绑定在同一笔 `0x1e` 请求的同一个 `B` 块上**，不存在“两边读不同请求”的脱节。

## 四、接手点三：`A[0x48]`（`0xbf075110`）与 `VBB +4`（`0xbf075100`）硬件语义及“低两位”最终裁决

真正决定“进编码器的像素是不是真 10-bit”的悬念，在于 **`A[0x48]`（`InputFormat` → `VBB +0` → `0xbf075110`）** 与 **`VBB +4`（`0xbf075100`）** 的分工。两边固件代码给出了完全吻合的硬件定义：

### 1. `VBB +0`（`0xbf075110`）与 `VBB +4`（`0xbf075100`）的真实硬件分工
在 `vcd_firmware.bin` 的 `vbb_drv.cxx` 中：
- **位深合法性校验函数 `0xe074`（含断言 `'bit_depth <= VdoBitDepth_10bit'` `0x1714b8` 及 8 项跳表 `0x1714d8`）**：
  - 分支 `0xe0c0`：仅当 `bit_depth == 0`（8-bit）时返回 `0`（`E_OK`），`bit_depth == 1` 返回 `1`（报错）。
  - 分支 `0xe0f0`：仅当 `bit_depth != 0`（即 `1`，10-bit）时返回 `0`（`E_OK`），`bit_depth == 0` 返回 `1`（报错）。
- **寄存器写入函数 `0xe6c0`–`0xe748` 与行对齐函数 `0xe7f8`**：
  - `0xe714` 将 `VBB +0`（`A[0x48]`）写入 **`0xbf075110`（DRAM 源帧解包格式寄存器）**。
  - `0xe740` 将 `VBB +4`（`0..3`）写入 **`0xbf075100`（VBB 输出至编码核的目标格式寄存器：`bit1 = is_422`，`bit0 = is_10bit`）**。
  - 当 `VBB +0 != 6`（源非 4:2:0）且 `VBB +4 >= 2`（目标为 4:2:2）时，`0xe6d4`–`0xe704` 额外配置 `0xbf0751b0` 色度相位/滤波寄存器；此外 `0xdc48` / `0xe3a4` 按 `0..1023`（`0x3ff`，每分量 10-bit）向 `0xbf075150` 写入画面边缘填充色。

将 `av-cam.bin` 的 `0x41bb04`–`0x41bc06` 与 `vcd_firmware.bin` 的 `0xe074`（`0x1714d8`）、`0xe7f8` 并排对照，`A[0x48]` 全部枚举值的物理含义彻底水落石出：

| `A[0x48]` (`InputFormat` / `0xbf075110`) | `av-cam.bin` (`0x41bb04`–`0x41bc06`) 生成条件 | `vcd_firmware.bin` `0xe7f8` 宽度对齐 | `vcd_firmware.bin` `0x1714d8` 位深判定 | 物理内存像素格式定义 |
|---|---|---|---|---|
| `0` | `compress == 2 && bit_depth == 0` | 32 px | `0xe0c0` (**8-bit**) | ISP 帧压缩格式 2（**8-bit**） |
| **`1`** | **`compress == 2 && bit_depth == 1`** | **32 px** | **`0xe0f0` (10-bit)** | **ISP 帧压缩格式 2（真 10-bit）** |
| **`2`** | **`compress == 3 && bit_depth == 1`**（`bd=0` 直接报错） | **32 px** | *(专用压缩模式)* | **ISP 帧压缩格式 3（`av-cam.bin` 仅限 10-bit）** |
| `3` | `compress == 1` **（完全不读 `bit_depth`！）** | 64 px | `0xe0c0` (**8-bit**) | **ISP 帧压缩格式 1（纯 8-bit）** |
| `4` | `compress == 0 && chroma == 1 && bit_depth == 0` | 2 px | `0xe0c0` (**8-bit**) | 未压缩 YUV 4:2:2（**8-bit**，16bpp） |
| **`5`** | **`compress == 0 && chroma == 1 && bit_depth == 1`** | **2 px** | **`0xe0f0` (10-bit)** | **未压缩 YUV 4:2:2（真 10-bit）** |
| `6` | `compress == 0 && chroma == 0` **（完全不读 `bit_depth`！）** | 2 px | `0xe0c0` (**8-bit**) | **未压缩 YUV 4:2:0（纯 8-bit）** |
| *(`7`)* | *(`av-cam.bin` 无生成分支)* | 2 px | `0xe0f0` (**10-bit**) | *(微码预留：未压缩 YUV 4:2:0 10-bit)* |

### 2. 上游 `SyncYCOut` + `CODEC V` 实锤：为什么 A7R3 内录拿不到像素低两位？
顺着 `av-cam.bin` 中计算 `A[0x48]` 的三个输入字段（`[r5+0x7b0] = compress`、`[r5+0x7b4] = chroma`、`[r5+0x7ac] = bit_depth`）向上游回溯至 `CODEC V`（`0xb59ec`–`0xb5a0e`）与 `SyncYCOut`（`0x3805e0`–`0x380674`），发现了 **三道硬性截断**：

1. **第一刀（`SyncYCOut` `0x38064c`–`0x380670` 锁死压缩模式为 `0` 或 `1`）**：
   `SyncYCOut` 读取上游配置 `+0x3c` 后：为零写 `StdYcInfo +0x2f = 0`，非零则执行 **`0x380658: movs r3, #0x1; strb.w r3, [r2, #0x2f]`**。也就是说，A7R3 的 `SyncYCOut` **永远只向 REC 帧描述填入 `compress = 0` 或 `1`，绝不会产生 10-bit 压缩所需的 `2` 或 `3`**。
2. **第二刀（`StdYcInfo +0x36` 恒为 `0` + 行跨度按 8-bit 16bpp 计算）**：
   此前已证全固件无任何代码向 `StdYcInfo +0x36` 写非零值（`MprIf::SetRecVideoBitDepth` 零调用），且下游 `0x5499e0`（`add.w r3, r1, r3, lsl #1`）固定按 `canvas_size_x * 2` 字节计算行跨度。
3. **第三刀（`CODEC V` `0xb5a0a` 硬编码输入色度为 `4:2:0`）**：
   在 `0xb5a00` 读取 `StdYcInfo +0x36` 之后，`0xb5a0a` 直接执行 **`movs r3, #0; str r3, [r4, #0x1c]`**，将传给 `Imola` 的输入帧 `chroma`（`[r5+0x7b4]`）**无条件写死为 `0`（4:2:0）**！

**把这三刀代入上表（`0x41bb04`–`0x41bb92`）**：
- 当 `compress == 1` 时，`0x41bb90` 无视 `bit_depth` 直接输出 **`A[0x48] = 3`（8-bit 压缩）**；
- 当 `compress == 0` 时，因 `chroma == 0`，`0x41bb48` 同样无视 `bit_depth` 直接输出 **`A[0x48] = 6`（8-bit 未压缩 4:2:0）**！

## 五、最终综合结论（针对内录位深与固件修改可行性）

1. **原厂 3.10 固件（含 S-Log2 / S-Log3 1080p 25p 及 4K 内录）**：
   REC 通道送入 `Imola` 的 `A[0x48]` 必为 `3` 或 `6`（均为 8-bit DRAM 源格式），`B` 块为 `100/1/0`（High Profile 4:2:0 8-bit），**全程为纯 8-bit 录制**。
2. **Imola 编码协处理器本身的潜力**：
   A7R3 机身内的 `Imola` 硬件与 `vcd_firmware.bin` 微码 **具备完整的真 10-bit 编码能力**（不仅 `0x99c74` 原生支持 AVC `High 10 (110)` 与 `High 4:2:2 (122)` 10-bit，微码内甚至完整保留了 `HEVC` 10-bit 编码器 `0x66c74` 及 `VBB RX` 的 10-bit 输入模式 `A[0x48] ∈ {1, 2, 5}`）。
3. **固件 Patch 解锁真 10-bit 内录的真实壁垒**：
   - **如果只 Patch 编码器参数表（让 `B` 变成 `110/2/2` 或 `122/2/2`）**：`VBB +4`（`0xbf075100`）与 `AVC 0x99c74` 会同步切到 10-bit 模式，录出的 MP4/XAVC 码流在 MediaInfo / FFmpeg 解码器看来会是合法的 `High 10` 或 `High 4:2:2 10-bit` 文件；**但由于 `A[0x48]`（`0xbf075110`）仍为 `3` 或 `6`，VBB 硬件从 DRAM 抓取的依然是 8-bit 像素，低 2 位只是硬件补零/重采样产生的“伪 10-bit（8-bit 装进 10-bit 容器）”，不会增加原始色阶精度**。
   - **若要获得保留低两位的真 10-bit**：除了修改 `B` 表项和 `CODEC V`（`0xb5a00`–`0xb5a0c` 放开 `bit_depth=1`、`chroma=1` 或 `compress=2/3`）使 `A[0x48]` 变为 `5` / `1` / `2` 之外，**核心前提是逆向并重配 BIONZ X 上游 ISP 硬件管线（`Sequence_Movie` → `SyncYCOut` 背后的 ISP 写 DRAM 寄存器与 DMM 帧缓冲分配器），让 ISP 真正往 DRAM 写出 10-bit 4:2:2 或 `compress=2/3` 10-bit 压缩帧**。在未重配上游 ISP 硬件寄存器前，仅靠编码侧或胶水层补丁无法凭空恢复已被 ISP 截断的低两位色阶。
