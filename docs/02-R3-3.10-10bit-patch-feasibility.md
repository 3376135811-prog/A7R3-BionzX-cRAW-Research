# ILCE-7RM3 (A7R3) 3.10 固件 Patch 解锁 10-bit 内录：全链路可行性评估报告

本报告基于 R3 3.10 解包固件（`av-cam.bin`、`/codec/vcd_firmware.bin`、`libmpr.so`、`nflasha3.img`）的完整静态逆向结果，评估“通过修改固件开启 A7R3 10-bit 内录”在芯片/DSP、ISP 管线、封装器与刷机链路四个层面的真实可行性。

---

## 一、重大发现：A7R3 的硬件编码器芯片/微码其实内置了 1080p 10-bit 4:2:2 能力

之前怀疑 A7R3 的硬件编码器（Bionz X 协处理器）可能在物理或 DSP 微码层面完全不支持 10-bit，**逆向结果推翻了“编码器硬件完全不支持”的假设，但也揭示了严格的规格边界**：

1. **A7R3 唯一启用的硬件视频编码器为 `Imola` (`UCP/VCD`)**：
   - 在 `TSKVIDENC` 初始化（`0x78b7c4`–`0x78b814` 与跳转表 `0x434830`）中，8 个编码器槽位里有 7 个（`ZIMA_AVC`、`IMOLA` 旧槽、`Beaune_I`、`CURIE`、`FPGA_DNXHD`、`FPGA_PRORES`、`ZIMA_DV`）被编译成了仅 4 字节的空桩对象（`0x4128dc`）。
   - 唯一实例化的真实编码器位于槽位 `2`（对象偏移 `+0x10`，大小 `0xee20` 字节，构造函数 `0x41b7c8`），其内部日志前缀为 `[IMLENCPRM]`，对应根文件系统 `/codec/vcd_firmware.bin`（Sony UCP/VCD `Astra` 平台编码器微码，编译时间 `2017/10/04`）。
2. **`vcd_firmware.bin` 微码明确包含 10-bit 编码支持**：
   - 微码内部断言包含 `bit_depth <= VdoBitDepth_10bit`（`venc_bitassign.cxx`），同时编译进了 `AVC` 与 `HEVC` 编码控制模块。
3. **`av-cam.bin` 的 `config_start_param_avc` 表（`0x85eed0`，共 148 行 × `0x64` 字节）中直接存有 23 组 10-bit 4:2:2 预设！**
   - **行 `[0..36]`（`stype = 0x04`，即消费级 XAVC S MP4）**：全部 37 组预设（含 4K 与 1080p）均为 `profile_idc = 100 (0x64, High Profile)`、`chroma = 1 (4:2:0)`、`bit_depth = 0 (8-bit)`。
   - **行 `[37..42]`（`stype = 0x05`，专业线 XAVC MXF 4K `3840x2160`）**：同样全部为 `profile_idc = 100`、4:2:0、8-bit——说明**这颗编码器 ASIC 在 4K H.264 下即使在专业机型（如 PXW-Z90）上也只支持 8-bit 4:2:0**。
   - **行 `[43..65]`（`stype = 0x05`，专业线 XAVC MXF `1920x1080` / `1920x540i` / `1280x720`）**：全部 23 组预设均为 **`profile_idc = 122 (0x7a, H.264 High 4:2:2 Profile)`、`level_idc = 41/42`、`chroma = 2 (4:2:2)`、`bit_depth = 1 (10-bit)`**（即 PXW-Z90 等同平台广播级手持机的 1080p 10-bit 4:2:2 预设残留）。

## 二、为什么“只改一两个字节”行不通？四大硬性关卡拆解

虽然编码器微码和预设表里有 1080p 10-bit 4:2:2 的底子，但要真正打通内录，横亘着 **4 道必须同时解决的关卡**（其中第 1 道和第 3 道难度极高）：

### 关卡 1（最大现实门槛）：固件重打包与非对称签名校验
- A7R3（内部型号 `0x71030013`）属于索尼第三代 `SYSASTRA` 架构，已彻底移除第二代机身（如 A7R2/A6300）时代的 Android 子系统与 `OpenMemories / pmca` 应用安装入口。
- 固件升级包 `FirmwareData_ILCE7RM3V310.dat` 内的 `FDAT` 镜像虽然可以用已知密钥**离线解密解包**用于静态逆向，但刷入相机时受索尼私钥签名保护。在没有刷机签名绕过手段或拆机硬件编程器（且需确认 Bootloader 对 `nflasha3` 内 `AV-CAM.BIN` 是否做启动验签）的前提下，**修改后的固件无法通过官方 USB 升级程序刷回机身**。

### 关卡 2：`Imola` 编码参数构造器的色度/位深耦合限制（`0x41bb04`–`0x41bc06`）
即使不考虑刷机问题，假设你只把 `REC` 描述的 `+0x36` 改成 `1`（让编码参数 `+0x50 = 1`），在 `create_imola_enc_start_param()` 中会发生什么？
- **在非压缩输入路径（`input_image_compress == 0`，`0x41bb08`）**：
  - `CODEC V` 在 `0xb5a0a` 硬编码写入了 `input_image_chroma = 0`（4:2:0）。
  - 在 `0x41bb46`–`0x41bb4a` 处，当 `compress == 0` 且 `chroma == 0`（4:2:0）时，**代码根本不读取 `input_image_bit_depth`（`[r5, #0x7ac]`），而是无条件把硬件 `input_format`（`[r4, #0x50]`）写成 `6`（8-bit 4:2:0）**！
  - 在 `compress == 0` 下，只有 `chroma == 1`（4:2:2，`0x41bb10`）才会读取 `bit_depth` 并映射为 `input_format = 5`（10-bit 4:2:2）；或者在索尼私有帧缓冲压缩模式 `compress == 2 / 3`（`0x41bb94` / `0x41bbd6`）下才会读取 `bit_depth == 1`。
- **在预设表匹配路径（`0x41c63a`–`0x41c81e`）**：
  - A7R3 主录像走 `stype = 0x04`（XAVC S），命中的 `config_start_param_avc` 行 `[0..36]` 全部把输出码流 SPS 写成 `High Profile (100)` + `8-bit`。H.264 标准语法中 `High Profile (100)` 严禁 10-bit（必须改为 `High 10 (110)` 或像行 `[43..65]` 一样改为 `High 4:2:2 (122)`）。

### 关卡 3（核心技术未知项）：上游 ISP (`VdfCh` → `SyncYCOut`) 是否真能向 DRAM 输出 10-bit 像素？
编码器只是消费者，它按 `addr_y` / `addr_c` 和行跨度 `line_size`（`+0x08`）去 DRAM 读图像：
- 如果只改编码器侧（把 `CODEC V` / `Imola` 改成读 10-bit 4:2:2），而上游 ISP（`VdfCh` 与 `SyncYCOut` `REC=1`）往内存里写的仍然是 **8-bit 4:2:0** 像素（每像素亮度 1 字节），编码器按 10-bit 4:2:2 位宽去 DMA 读取就会立刻出现**行跨度错位、画面撕裂花屏甚至内存越界死机**。
- 更关键的是：A7R3 连 **HDMI 外录输出都只支持 8-bit 4:2:2**（而不像 GH5 / A7S3 支持 10-bit HDMI 输出）。这意味着必须在固件中核实：上游图像管线 `VdfCh::InputSetYuvLayoutOptionComp` 与 `SyncYCOut`（`0xd8d8e8` → `+0x80` → `+0x2e` 的 6 种枚举 `{2,0,1,6,3,4}`）中，**到底存不存在 10-bit 内存输出模式及对应的帧缓冲尺寸分配逻辑**。如果 ISP 硬件寄存器配置在 A7R3 上只编译了 8-bit YC 输出，或者在 ISP 末端就已经截断到 8-bit，那么后端编码器怎么改都拿不到真 10-bit 数据。

### 关卡 4：Linux 侧 MP4/XAVC S 封装器限制（`libmpr.so`）
- `libmpr.so` 中的 `FeaCore::SetRecVideoBitDepth`（`0x521b22`–`0x521b34`）对录像格式做了硬白名单检查：只允许内部编码枚举 `1` 或 `5`（对应专业线 MXF / MPEG2 / SSTP），消费级 XAVC S MP4 直接返回错误码 `0xa`。
- 若将 `stype = 0x04` 的编码预设强行改为 `High 4:2:2 Profile (122)` 10-bit，还需核查 MP4 封装器（`AviMMgr` / `RecLib`）在生成 `avcC` 描述符及索尼 XAVC S 元数据时是否会校验 `profile_idc == 100` 而拒绝录制报错。

## 三、综合评估与下一步建议

| 评估维度 | 结论 |
|---|---|
| **4K 10-bit 内录可能性** | **几乎为零**。连共享同一套 `Imola` 编码微码的专业机预设（`stype=0x05` 3840×2160）都只有 8-bit 4:2:0，属于这代 Bionz X 编码硬件上限。 |
| **1080p 10-bit 内录硬件潜力** | **编码器 DSP 层存在真实支持**（`vcd_firmware.bin` 支持 10-bit，且 `0x85eed0` 行 `[43..65]` 自带现成的 1080p 10-bit 4:2:2 H.264 High 4:2:2 预设）。 |
| **实际落地难度** | **极高（研究级硬核工程）**。不是改单个开关就能开的功能，而是需要：① 确认上游 ISP/`SyncYCOut` 能输出 10-bit 4:2:2（或 10-bit 压缩帧）到 DRAM；② 联动修改 `SyncYCOut` + `CODEC V` + `config_start_param_avc` + `libmpr.so` 封装校验；③ 解决第 3 代机身固件签名刷写问题。 |

### 如果你想继续做纯技术逆向验证，最值得追的“生死判据”只有两个：
1. **核查 ISP / `SyncYCOut` 是否具备 10-bit 像素输出能力**：追踪 `0xd8d8e8`（`+8` → `+0x80`）和 `SyncYCOut` `+0x2e` 的 6 种格式枚举（`{2,0,1,6,3,4}`）被谁消费（特别是帧缓冲区大小 `line_size` 计算与硬件寄存器配置），看里面是否包含 10-bit 4:2:2 格式（可与你工作目录里已有的 **PXW-Z90** 资料交叉比对，因为 Z90 就是同代芯片开启了 `stype=0x05` 1080p 10-bit 4:2:2 的参照系！）。
2. **确认你手头是否有刷入自定义修改实验的条件**：如果没有物理调试/刷写手段，这项工作目前只能作为**架构逆向研究**（彻底搞清索尼如何在同代芯片上刀法切割 A7R3 与 PXW-Z90），而无法直接变成可刷入相机的实用补丁。
