# Sony α7R III (ILCE-7RM3) v3.10 固件静态逆向报告（四）
## `SyncYCOut` 参数源头、`StdYcInfo` 真实字段语义与 BIONZ X ISP (`WrapRcBase` / `RcDriver`) 硬件位深底牌

- **分析对象**：`Update_ILCE7RM3V310.dmg` 解包产物 `AV-CAM.BIN`（即 `r3-310-decoded/static-view.o`，文件头含 `0x34` 字节包装头，真实运行加载基址 `VMA = 0x635c6000`）
- **分析方式**：100% 纯离线静态反汇编与数据流追踪（未连接相机、未刷机、不含任何签名绕过或攻击代码）
- **核心目标**：完成路线图**第一大部分（摸清 BIONZ X ISP 硬件底牌）**：
  1. 追查普通录像 `Sequence_Movie` 传给 `SyncYCOut`（通道 `1 = REC`）的参数源头（尤其是 `[r2, #0x80]` 与 `ycCompress`）；
  2. 彻底拆解 `StdYcInfo`（`PIN_YC_IMAGE_SIZE_INFO`，`0x3c` 字节）全部字段与 `+0x2e` 六种取值的真实语义；
  3. 深入 BIONZ X 底层硬件封装 `WrapRcBase` 与硬件寄存器驱动 `RcDriver` / `RcCalc` / `RcHwAccess`，核查 **A7R3 的 ISP 写内存通道到底有没有真 10-bit YUV 输出能力，索尼究竟在哪一层砍掉了它**。

## 一、核心结论速览

1. **重大勘误与真相还原：`StdYcInfo +0x2e` 根本不是像素格式，而是画幅宽高比 `aspect`！**
   - 在 `AV-CAM.BIN` 的 `0x08ef90–0x08f160` 找到了索尼官方的 `StdYcInfo` 诊断打印函数：
     - `0x08f07c` 读取 `[r7, #0x2e]` 并打印 **`aspect =%d`**（因此 `SyncYCOut` 在 `0x3805bc–0x38064a` 把上游 `0..5` 映射为 `{2, 1, 0, 3, 6, 4}` 只是画幅比例编码，并非 YUV 像素排布）。
     - 真正描述像素传输、排布、压缩与位深的字段是：`+0x2f`（`ycCompress`）、`+0x30`（`dataTransfer`）、`+0x31`（`dataPlacement`）、`+0x32`（`dataContent`）以及 `+0x36`（`input_image_bit_depth`）。
2. **`Sequence_Movie` → `SyncYCOut` 实时录像链路被软件硬性钳死在 8-bit**：
   - `Sequence_Movie`（`0x370df8–0x371208`）从 `[r4, #0x164]`（源自 `ImageParam_Sync.cpp` `0x35f884` 读取的 `[r2, #0x80]`，经 `0x3820f0` 校验仅允许 `{0, 1, 2, 4}`）填入 `SyncYCOut` 入参 `+0x38`（画幅比例）；从 `[r4, #0x140]`（源自模式表 `+0x14` 字节，`0x764ce6`）填入入参 `+0x3c`（`ycCompress`）。
   - `SyncYCOut::SetParam`（`0x38064c–0x3806d6`）将 `+0x2f`（`ycCompress`）**硬性钳制为 `{0, 1}` 布尔值**，`+0x30..+0x32` 仅能生成标准 8-bit 4:2:2 `(1, 1, 2)` 或 4:2:0 `(0, 0, 1/0)`，且**全程不写 `+0x36`（恒为初值 `0` = 8-bit）**。
   - 同时，`SyncYCOut` 并不会在主核直接写 ISP 寄存器，而是把通道配置存入 `0x109a384 + ch * 6`，通过 `CAIF`（`CaifCom::SndEvent`，`0x1e568` / `0x35c39c`）发给协处理器固件 **`bonobo.bin`**，并由 `0x35c6ba` 按 **8-bit 未压缩（16bpp）或 8-bit 压缩**向 DMM 申请录像帧缓冲内存。
3. **BIONZ X ISP (`WrapRcBase` / `RcDriver`) 硅片级硬件底牌：无 10-bit 未压缩 YUV 输出，但内置一套 10-bit DCE 硬件块压缩引擎！**
   - 拆解 `WrapRcBase`（`0x120a7c` `SetYcCompress`、`0x120b14` `SetTransfer`）与底层 `RcDriver` / `RcCalc` / `RcHwAccess`（`0x45afd4`、`0x467660`、`0x468ed4`、`0x794564–0x7952d8`）证实：
     - **未压缩写内存模式（`YcCompress <= 2`，硬件寄存器 bit 30 = `0`）**：`0x7952b4` 将像素位宽硬编码为 **`0x10`（16 bits/pixel，即 8-bit Y + 8-bit C 4:2:2）**。硬件寄存器打包器 `0x79458e` 与校验器 `CheckOutputImageType`（`0x468ed4` / `0x466de8`）中**不存在任何 10-bit 未压缩 YUV（如 20bpp packed 或 32bpp padded）输出格式**。这也解释了为何整代 BIONZ X 机型（含 A7R3/A7M3）连 HDMI Clean Out 也只有 8-bit。
     - **DCE 硬件块压缩写内存模式（`YcCompress` 为 `3/4/5`，硬件寄存器 bit 30 = `0x40000000`）**：在 `RcCalc` 的 DCE（Data Compression Encoder）计算函数 **`0x45afd4`** 中，除了 16bpp（8-bit 4:2:2，`0x45b04e`）和 8bpp（8-bit 单分量，`0x45afde`）外，**明确存在第三条硬件分支（`0x45b012–0x45b048`）**：当 `Transfer.mode != 0` 且 **`submode == 6`** 时，向 `[r1, #0x154]` 写入 **`10`（`0x0a` bits/sample，真 10-bit 分量位深！）**，由 `0x7946fc` 按 `(width * 10) >> 3` 及每 32 个采样 **`(32 * 10) >> 3 = 40` 字节**打包进硬件寄存器，并在 `0x79476c` / `0x794792` 将 `submode == 6` 映射为硬件位深码 `2`！
   - **为什么这套 10-bit DCE 在原厂录像中没有启用，且与编码器前端 `A[0x48]` 如何对应？**
     - 对照报告 `03` 中 `create_imola_enc_start_param`（`0x41bb04–0x41bc06`）与 `vcd_firmware.bin` `vbb_drv.cxx`（`0xe074`）的结论，两套硬件密码严丝合缝地对上了：
       - **`A[0x48] = 5`（10-bit 未压缩 4:2:2）**：虽然下游 `Imola VBB` 支持，但上游 **A7R3 的 BIONZ X `RC` 硬件根本没有 10-bit 未压缩 YUV 写内存模式**（此路在硅片层物理不通！）；
       - **`A[0x48] = 1 / 2`（对应 `ycCompress = 2 / 3` 的 10-bit 硬件压缩源）**：恰好与 `WrapRcBase` `0x121850` 特判的 `YcCompress ∈ {2, 3}` 及 `RcCalc` `0x45b012` 的 **`submode = 6`（10-bit DCE，32 采样 = 40 字节）** 一一对应！也就是说，**BIONZ X 的 `RC` 写内存核与 `Imola` 的 `VBB RX` 读内存核之间，在硅片设计上确实共享同一套 10-bit DCE 帧压缩协议！**
     - 但在 A7R3 的实时视频固件中，索尼在主核与协处理器两侧同时锁死了这条通路：`SyncYCOut`（`0x380658`）把 `+0x2f`（`ycCompress`）钳死在 `{0, 1}` 且不写 `+0x36`（`0`），`CODEC V`（`0xb5a0a`）硬编码 `chroma = 0`，而负责实时视频采集缩放的协处理器固件 **`bonobo.bin`** 通过 `CAIF`（`0x109a384 + ch * 6`）交互时也未暴露 10-bit DCE 开关。

## 二、证据链一：普通录像参数块 → `SyncYCOut` 源头追踪

*(注意：以下文件内代码偏移均指 `static-view.o` 内 `.text` 相对偏移 `off`，对应文件物理偏移 `0x34 + off`，运行期虚拟地址 `VMA = 0x635c6000 + off`。)*

### 1. `Sequence_Movie` 构造 `SyncYCOut` 入参（`0x370df8–0x371208`）

在 `Sequence_Movie` 配置主录像通道 `REC = 1` 时：

| 指令偏移 | 关键指令 / 调用 | 作用与数据流向 |
|---|---|---|
| `0x370df8–0x370e0c` | `ldr r0, [r4, #0x140]` → `cbz` 分支调用 `0x75ff46(w)` 或 `0x75bec4(w, 64)` | 读取 `Sequence_Movie` 对象的 `+0x140`（`ycCompress` 标志）：若为 `0`，按 64 像素对齐计算未压缩 `canvasSizeX`；若非 `0`，按压缩块跨度计算 `canvasSizeX`。 |
| `0x370e36` | `ldr r3, [r4, #0x164]` → `str r3, [sp, #0x7c]` | 将画幅比例枚举存入栈帧 `sp + 0x44` 的 **`+0x38`** 偏移。 |
| `0x370e3a` | `ldr r3, [r4, #0x140]` → `str r3, [sp, #0x80]` | 将 `ycCompress` 标志存入栈帧 `sp + 0x44` 的 **`+0x3c`** 偏移。 |

### 2. `[r4, #0x164]` 与 `[r4, #0x140]` 的上游赋值点

- **`[r4, #0x164]`（对应此前待查的录像参数块 `+0x80`）**：
  - 在 `ImageParam_Sync.cpp` 的 `0x35f884`：从上游录像模式配置块 `r2 = [r5, #0x08]` 读取 **`[r2, #0x80]`**，经 `0x3820f0`（断言文件名 `../Utility/EnumConverter.h`，仅接受 `{0, 1, 2, 4}` 四种合法画幅枚举，传入 `3` 会报错拦截）转换后写入 `Sequence_Movie` 的 `+0x164`。
- **`[r4, #0x140]`（`ycCompress` 开关）**：
  - 在 `0x764ce6`：根据录像规格索引检索 `0x24` 字节一组的 `ImageParam_Sync` 模式表（GOT 指针位于 `VMA 0x64337aac`，由启动期自 `0x63f7de55` 解压的数据段填充），读取表项 **`+0x14`** 字节（布尔值 `0` 或 `1`）写入 `[r4, #0x140]`；其余普通路径（`0x36e270`、`0x36f772`）直接写 `0`。

| `StdYcInfo` 偏移 | 类型 | 官方打印字段名（`0x08ef90`） | `SyncYCOut::SetParam`（`0x3803dc`）写入逻辑 |
|---|---|---|---|
| `+0x00` | `u8` | `valid` | `0x38045e` 写 `1` |
| `+0x04` | `u32` | `offset` | DMM 帧缓冲偏移（`0xd8de0c + ch * 0x28`） |
| `+0x08` | `u16` | `dmmId` | DMM 内存块句柄 ID |
| `+0x18`, `+0x1a` | `2×u16` | `canvasSizeX`, `canvasSizeY` | 画布宽高（内存行跨度像素数与高度） |

### `SyncYCOut` 与协处理器 `bonobo.bin` 的真实分工

进一步追踪 `SyncYCOut` 全文（`0x3806d6–0x381ac0`）与 `0x30fe48–0x310260` 发现：
1. `SyncYCOut::SetParam`（`0x3806d6–0x380796`）除了填写 `StdYcInfo` 外，只向全局 4 通道简表 **`0x109a384 + ch * 6`**（每通道仅 6 字节！）写入逐行/隔行、`ycCompress`（`0..3`）及 `422/420` 布尔位，并在 `0x35c6ba`（调用 `0x76429c` / `0x35c2cc`）按 **8-bit 帧尺寸**分配 DMM 环形缓冲。
2. 实时视频/取景的传感器采集与缩放写内存硬件动作，由独立运行在 BIONZ X 协处理器上的固件 **`bonobo.bin`** 执行；主核通过 `CAIF`（`CaifCom::SndEvent`，`0x1e568` / `0x381a38`）收发事件。当 `bonobo.bin` 把一帧写完到 DRAM 后，发回 `0x1000` 类消息唤醒 `0x30ff5c` → `SyncYCOut`（`0x381392`），后者把 DMM 帧连同 `StdYcInfo` Pin（`0x3813f8`）和 `0xd0` 字节时码状态 Pin（`0x381494`）通过 `0x310494`（`REC` 通道）推给编码器入口 `enc/sfmc_enc_input_yc.cpp`（`0xbc4f6` → `0x66f3e0` → `0x648998`）。

## 四、证据链三：BIONZ X `RC` 引擎（`WrapRcBase` + `RcDriver`）硬件位深与压缩核查

为了查明 BIONZ X **硅片硬件本身**在写内存（Resize & Convert → DRAM）时究竟支持多少位深，我们完整逆向了 `WrapRcBase.cpp`（`0x120a7c–0x12196c`）及其底层寄存器驱动 `src/api_rc.cpp`、`src/RcCalc.cpp`、`src/RcResize.cpp`、`src/RcResizeDst.cpp`、`RcHwAccess`（`0x45943c–0x469850` 与 `0x794518–0x795380`）。

### 1. 封装层接口：`WrapRcBase::SetYcCompress` 与 `SetTransfer`

- **`WrapRcBase::SetYcCompress`（`0x120a7c`）**：
  - `cmp r5, #5; bhi 0x120aac` —— 底层硬件驱动共支持 **`0..5` 六种 `YcCompress` 枚举**！（注意对比：`SyncYCOut` 只暴露了 `0..1`）。
  - 在 `WrapRcBase` 执行函数 `0x121850` 中，当输入或输出的 `YcCompress` 属于 `{2, 3}` 时，额外传入 `+0xbc` 压缩率控制参数块调用 `0x794518`（`api_rc`）。
- **`WrapRcBase::SetTransfer`（`0x120b14`）**：
  - 将像素传输格式拆为两个 `u32`（写入 `[r3]` = `mode` 与 `[r3, #4]` = `submode`）：
    - `r1 == 0` → `mode = 0, submode = 0`（标准 16bpp YC 4:2:2 交织）
    - `r1 == 1` → `mode = 1, submode = 0`（8-bit Y/C 分离）
    - `r1 == 2, r2 = 1..12` → `mode = 2, submode = 0..11`（12 种扩展子格式！）

### 2. 未压缩路径（`YcCompress <= 2`）：硬件锁死 8-bit（16bpp），无 10-bit 未压缩 YUV！

在 `RcHwAccess` 寄存器位域打包器 `0x794564–0x7945d6` 与像素跨度计算器 `0x7952b4` 中：
- `0x79456e` / `0x794592` 检查 `[r1, #0x4]`（内部 `yc_compress` 标志）：
  - 当 **`yc_compress <= 2`** 时，`[r4, #0x1c] = 0`，且硬件控制寄存器 **bit 30 清零**（`bfi r3, r0, #30, #1`，即关闭 DCE 硬件压缩器，直接输出未压缩数据），仅用 bit `[23:22]` 编码 `mode = 0/1/2`（4:2:2 / 4:2:0）。
  - 紧接着在 `0x467a6a` / `0x467a7c` 调用 **`0x7952b4`** 计算行跨度：当未启用 DCE 压缩（`r2 <= 1`）时，`0x7952c4` **无条件固定传入 `movs r1, #0x10`（16 bits/pixel = 8-bit 4:2:2）**！
  - 同时，虚表槽 `+0x20` 的输出图像格式校验器 `RcResize::CheckOutputImageType`（`0x468ed4`）与 `RcResizeDst::CheckOutputImageType`（`0x466de8`）只检查 64 像素 / 8 字节 / 2 像素对齐与宽高上限 `0x1ffc`（8188 像素），**没有任何 10-bit 未压缩 YUV 打包或对齐分支**。

> **结论 A**：A7R3 的 BIONZ X `RC` 硬件写内存单元**物理上不支持未压缩 10-bit YUV（如 Y210 / v210 / P010）输出**。所有未压缩 YUV 落盘/落 DRAM 通道在硅片层面均为 8-bit。

### 3. 硬件块压缩路径（`YcCompress > 2`）：发现隐藏的 **10-bit DCE（`submode == 6`）** 硬件能力！

当 `yc_compress > 2` 时，`0x7945d2` 将硬件控制寄存器设为 **`0x40000000`（置位 bit 30，开启 BIONZ X DCE 硬件块压缩编码器）**，并在 `0x467bca` 调用 **`0x45afd4`（`RcCalc::CalcDce` 位深与块长计算函数）**，随后在 `0x467be8` 调用 **`0x7946fc`（DCE 寄存器打包函数）**！

请看 `0x45afd4–0x45b0c6` 与 `0x7946fc–0x7947a8` 的精确指令级证据：

```arm
@ === 0x45afd4: RcCalc DCE 采样位深 ([r1, #0x154]) 计算 ===
45afd4: ldr   r0, [r1, #0x8]        @ r0 = Transfer.mode
45afd6: ldr   r3, [r1, #0x58]       @ r3 = Transfer.submode (0..11)
45afd8: cbz   r0, 0x45b04a          @ 若 mode == 0 -> 跳转 16bpp 分支

@ 分支 1: mode != 0, submode <= 1 -> 8-bit 分量压缩
45afda: cmp   r3, #0x1
45afdc: bhi   0x45b012
45afde: movs  r3, #0x8              @ 位深 = 8 bits!
45afe2: str.w r3, [r1, #0x154]      @ [r1, #0x154] = 8
...

@ 分支 2: mode != 0, submode == 6 -> 真 10-bit 分量压缩!!
45b012: cmp   r3, #0x6
45b014: d160  bne 0x45b0d8          @ 其他 submode 直接返回错误码 4!
45b016: adds  r3, #0x4              @ r3 = 6 + 4 = 10 (0x0a = 10 bits)!!
45b01a: str.w r3, [r1, #0x154]      @ [r1, #0x154] = 10!!

@ 分支 3: mode == 0, submode == 0 -> 8-bit 4:2:2 交织压缩 (16bpp)
45b04a: cmp   r3, #0x0
45b04c: bne   0x45b0dc
45b04e: adds  r3, #0x10             @ r3 = 16 (0x10 = 16 bits/pixel)
45b050: str.w r3, [r1, #0x154]      @ [r1, #0x154] = 16
```

紧接着看 `0x7946fc` 与 `0x79476c / 0x794792` 如何使用 `[r1, #0x154] = 10` 填写硬件寄存器：
1. **按 10-bit 计算压缩块字节跨度（`0x7946fc–0x79473e` 及 `0x45b0b0–0x45b0c0`）**：
   - `r0 = (width * [r1, #0x154]) >> 3` = `(width * 10) / 8` 字节写入寄存器描述 `[r3, #0x14]`、`[r3, #0x18]`；
   - `r2 = ([r1, #0x154] << 5) >> 3` = `(10 * 32) / 8 = 40`（`0x28` 字节 / 32 像素微块）写入 `[r3, #0x1c]`！
2. **向硬件寄存器写入 10-bit 模式码（`0x79476c` 输入端 DCD / `0x794792` 输出端 DCE）**：
   - `cmp r4, #0x6; subs r4, #0x4; str r4, [r2]`：当 `submode == 6`（10-bit）时，向硬件寄存器字段写入 **`2`**（而 `submode == 1` 8-bit 写入 `0`）！

> **结论 B**：A7R3 的 BIONZ X ISP 芯片内部**确实拥有真 10-bit 硬件写内存通路**，但它**仅存在于 DCE（Data Compression Encoder）私有块压缩模式下（`submode == 6`，每 32 采样打包为 40 字节，硬件位深码 `2`）**，主要供静态拍照（`still_dda_rc.cpp`）及 ISP 内部多遍降噪/合成在 DRAM 中周转高精度图像使用。

## 五、全局拼图闭环：索尼到底在哪几层砍掉了 A7R3 的 10-bit 内录？

结合本系列四份报告（`01` 至 `04`），A7R3 从传感器/ISP 到 H.264 编码器的全链路架构真相已经**彻底闭环，无任何盲区**：

| 管线层级 | 固件模块与核心地址 | 硬件/微码真实能力 | A7R3 固件实际状态（被砍位置） |
|---|---|---|---|
| **1. BIONZ X ISP 缩放与写内存硬件 (`RC`)** | `AV-CAM.BIN` `WrapRcBase` (`0x120a7c`, `0x121850`) + `RcDriver` (`0x45afd4`, `0x7946fc`, `0x7952b4`) | **未压缩 YUV 仅限 8-bit (16bpp)**（故 `A[0x48]=5` 在 ISP 侧物理不存在）；**唯一 10-bit 写内存能力是私有 DCE 块压缩 (`YcCompress=2/3`, `submode=6`, 10-bit)** | 未压缩 10-bit 被硬件物理封死；真 10-bit 仅存在于 DCE 块压缩模式 |
| **2. 实时视频采集协处理器与同步输出 (`bonobo.bin` ↔ `SyncYCOut`)** | `Sequence_Movie` (`0x371208`) → `SyncYCOut` (`0x3803dc`) ↔ `CAIF` (`0x109a384`) | 仅配置并传递 8-bit 未压缩 (`0`) 或 8-bit 压缩 (`1`) | **第一道闸门**：`SyncYCOut` (`0x380658`) 把 `ycCompress` 钳死在 `{0,1}`，不写 `StdYcInfo +0x36` (`0`)，`CAIF` 6 字节通道表无 `submode=6` 字段，DMM (`0x35c6ba`) 仅分配 8-bit 缓冲 |
| **3. 视频编码胶水层与 `0x1e` 参数生成 (`CODEC V` → `imola_enc_param`)** | `AV-CAM.BIN` `0xb59ec–0xb5a0c` → `0x41ba4c` (`create_imola_enc_start_param`) | `0x41bb04` 支持在 `compress=2/3` 时输出 `A[0x48]=1/2`（10-bit DCE 压缩源），`0x85eed0` 表含 `122/2/2` 10-bit 项 | **第二道闸门**：`0xb5a0a` 硬编码 `chroma=0` (4:2:0)，叠加 `compress ∈ {0,1}` 与 `bit_depth=0`，锁死 `A[0x48] ∈ {3, 6}`（全为 8-bit 源） |
| **4. H.264 硬件编码器与前端 (`Imola` VCD + `VBB RX`)** | `vcd_firmware.bin` `0xdf8d0` → `0xec348`/`0xec464` (`VBB`) + `0xee6ec` → `0x99c74` (`AVC`) | `VBB RX` (`0xbf075110`, `0xe074`) 原生支持解压 `A[0x48]=1/2` (10-bit DCE)，`AVC` 支持 `High 10` (`110/2/2`) 与 `High 4:2:2` (`122/2/2`) | 下游编码器硬件与微码“刀枪俱全”，但因上游第 1、2、3 层只产生 8-bit 帧与 `A[0x48]=3/6`，永远走 8-bit 分支 |

### 对“能否通过修改固件（Patch）解锁真 10-bit 内录”的最终架构级定论

1. **为什么只改主核 `AV-CAM.BIN` 几个字节（例如强改 `+0x36 = 1`、放开 `0xb5a0a` 并选 `110/2/2` 或 `122/2/2`）绝对拿不到真 10-bit？**
   - 首先，**`A[0x48] = 5`（10-bit 未压缩 4:2:2）这条路已经被证伪**：A7R3 的 BIONZ X `RC` 硬件写内存单元在未压缩模式下固定 16bpp（8-bit），根本吐不出未压缩 10-bit YUV。
   - 其次，如果不动协处理器固件 **`bonobo.bin`**，DRAM 里的录像帧物理上依然是 `bonobo.bin` 写出的 8-bit 数据；单方面在主核把 `A[0x48]` 改成 `1/2/5` 只会让 `VBB RX` 按 10-bit 步幅误读 8-bit 内存，导致花屏/条纹或硬件报错。
2. **全机唯一真实存在的 10-bit 硬件通路在哪里？（供后续与 GPT 深入研讨）**
   - 本次逆向最核心的发现是：**BIONZ X 的 `RC` 引擎确实内置了 `submode = 6`（`YcCompress = 2/3`）10-bit DCE 硬件块压缩（每 32 采样 = 40 字节），且恰好与 `Imola VBB RX` 的 `A[0x48] = 1 / 2`（`compress = 2 / 3` 10-bit 压缩输入）形成硬件级配对！**
   - 但要评估这条唯一硬件暗道能否在实时录像中被唤醒，必须进入**协处理器固件 `bonobo.bin`**（位于同分区 `nflasha3.img` 内）：
     1. 核查 `bonobo.bin` 中负责实时视频流的 `SGC / RCCT` 硬件流水线是否允许在传感器实时读出速率下对 `REC` 通道开启 `YcCompress = 2/3` + `submode = 6`（10-bit DCE），还是该模式仅限离线 `RCRT`（拍照回放/多帧降噪）使用；
     2. 若 `bonobo.bin` 支持，则需同步联动修改 **① `bonobo.bin` 实时 ISP 通道配置、② `AV-CAM.BIN` `SyncYCOut` 的 DMM 帧缓冲尺寸（`0x35c6ba`）与 `StdYcInfo`（`+0x2f = 2/3`, `+0x36 = 1`）、③ `CODEC V`（`0xb5a0a`）与 `Imola` 表索引**。这属于跨双核固件的深度系统工程，而非单点开关补丁。
