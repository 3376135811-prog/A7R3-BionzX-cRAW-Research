# Report 05: Sony α7R III (ILCE-7RM3) v3.10 — `bonobo`/`dfe` 协处理器真身与实时视频 `RCCT` 10-bit DCE 架构可行性终审报告

> **研究性质声明**：本报告基于离线解包固件的纯静态硬件架构与软件管线逆向分析（Static Architectural Reverse Engineering），仅用于评估 BIONZ X ("Astra" SoC) 硅片数据通路与固件状态机的客观技术边界，不涉及任何固件修改、签名绕过或刷机操作。

## 0. 核心终审结论（Executive Verdict）

针对前序交接文档 `00-START-HERE-NEW-CHAT.md` 与 `04-R3-3.10-SyncYCOut-ISP-hardware.md` 提出的终极悬念——**“实时视频管线（`RCCT` / `RCH` / `RCV`）能否开启 BIONZ X `submode=6` (`YcCompress=2/3`) 的 10-bit DCE 硬件块压缩，从而实现真 10-bit 视频内录？”**——经对 `AV-CAM.BIN` (`static-view.o`)、`bonobo.bin`、`dfe_app.bin`、`dfe_dat.bin` 及 `vcd_firmware.bin` 的指令级全量逆向，得出确定性结论：**不能（架构级不可行）**。

本轮逆向同时推翻了前期假说中的四处关键误判，并定位到决定 α7R III 视频位深上限的真实硅片边界：

1. **`bonobo.bin` 与 `dfe_app.bin`/`dfe_dat.bin` 均与后端 YCbCr 10-bit DCE 压缩无关**：
   - `bonobo.bin` (`172,144` B) 并非 ISP 图像协处理器固件，而是 **Renesas H8S/2600 (H8SX) Big-Endian 机电控制 MCU 固件**，通过 `0x39` 同步字、`0x22` (34) 字节定长串口协议与 `AV-CAM.BIN` (`BonoboDSP_Send`/`Rcv` `@0x2ad868`) 通信，专职机身五轴防抖 (`Bear`)、快门/光圈/镜头驱动与拨轮采样，完全不接触图像像素流或 DRAM。
   - `dfe_app.bin` (`1,956` B) 与 `dfe_dat.bin` (`65,536` B) 是 **Little-Endian ARMv7 (ARM32 异常向量 + Thumb-2 指令集，本地 TCM/SRAM 映射于 `0xfe1e0000–0xfe1fffff`) 的传感器数字前端 (Digital Front End, DFE) 微码**，位于 CMOS (`IIF`/`SGC`) 与 `CamCore` 之间，仅负责传感器 `HD/VD` 时序、片上相位对焦 `ZPD1` 中断 (`DFE_INT0/1`) 及 **Bayer RAW 域压缩 (`rdcEncType`)**。
2. **`0x109a384` `"CAIF"` 并非子系统框架，`0x765ab6` 并非 `rcct_resize`**：
   - `static-view.o` 全段采用统一平坦加载基址 **`VMA = 0x635c6000`**（文件偏移 `0x34 + text_off`）。
   - `.text+0x109a384` 处的 `"CAIF"` 只是静态结构体 `CAIF_DRV_STATIC_DATA` 的 4 字节魔数头；前期猜测的 `0x765ab6` 实为单条 `bx lr` (`0x4770`) 空桩函数。真正的 `RC` 驱动硬件层全部静态链接在主核 `AV-CAM.BIN` 的 `0x458000–0x46d000` 与 `0x794400–0x798100`。
3. **参数语义纠偏：`Sequence_Movie` 写入的 `2` 是 `RC_IP_TYPE_IP`（片上流式直连），而非 `YcCompress=2`**：
   - `Sequence_Movie` 在 `@0x3632e8–0x363300` 写入 `[r4, #0x700] = 2`、`[r4, #0x800] = 2`（传入 `[rcct, #0x54]` / `[rcct, #0xa0]`），由官方报错字符串 `@0x4670f6` (`"Not RC_IP_TYPE_IP: 8byte alignment\n"`) 证实为 **`ip_type = 2` (`RC_IP_TYPE_IP`，即不落 DRAM、走片上 eSRAM VMC / IP-to-IP 硬件直连)**。
   - 真正的压缩子模式位于 `[rcct, #0x50]` (`in_submode`) 与 `[rcct, #0x9c]` (`out_submode`)。在实时视频初始化 `@0x36e270` 与 `@0x36f772` 中，`[r4, #0x140]` 被成功返回码 `r8 = 0` 恒定清零（未压缩 8-bit YC），即使在落 DRAM 分支也仅能切换至 `submode = 1`（8-bit 64px 对齐 DCE 块压缩）。
4. **四重硅片与全链路硬约束封死实时视频 10-bit 内录**：
   - **约束一（`RCH`/`RCV` 硅片无 10-bit/扩展 DCE 硬件单元）**：全芯片 14 个 `RC`/`DST` 引擎（`EXEC[0..13]`）中，常规实时视频缩放引擎 `RCH`/`RCV` (`EXEC[5..10]`, MMIO `0xf3880000` / `0xf3980000`) 的硬件能力字 **`caps & 0x800 == 0`**，且 `RcResize::CalcRegister` (`@0x794f9e` / `@0x7952e6`) 根本没有 `submode=6/7/8` 编码逻辑；全芯片仅单套镜头畸变校正引擎 **`DST` (`EXEC[11..13]`, MMIO `0xf3500000`, `caps & 0x800 != 0`)** 支持 `submode=6/7/8`。同时软件包装层 `WrapRcBase::SetYcCompress` (`@0x120a7c`) 将 `RCCT` 压缩枚举硬限制在 `0..5`，直接拦截 `>=6`。
   - **约束二（`RC_IP_TYPE_IP` 流式直连不经过 DRAM DCE 打包器）**：实时视频主干 `APL -> RCH -> RCV -> VFX` 通过 `ip_type = 2` 片上直连握手传输像素，不经过 DRAM DMA 块压缩单元。
   - **约束三（视频中游 `APL`/`Spica`/`VFX` 固定按 8-bit YCbCr 寻址）**：14-bit RAW 在 `CamCore` 内完成 S-Log2 / S-Log3 / HLG 映射后，视频模式 `APL` (`apl_mov_set_aic` `@0x375e74`)、`Spica` 电子防抖与 `VFX` (`vfx_4k_movie_prm_gen` `@0x16c02c`) 全部运行在 8-bit YCbCr 数据平面上。
   - **约束四（后端硬件编码器 `Imola VCD` 与 XAVC S H.264 管线锁死 8-bit 4:2:0）**：尽管 `vcd_firmware.bin` 底层微码含有 Astra SoC 通用的 HEVC 与 `'bit_depth <= VdoBitDepth_10bit'` 断言代码，但 α7R III 视频录制仅启用 H.264/AVC (`CodecType=1`)，其 4K 通道配置表 (`@0x1125d68`) 与 `ImolaCreateCh` (`@0x41243a–0x412550`) 硬编码 `BitDepth = 0` (8-bit)、`ChromaFormat = 1` (4:2:0)，且 VCD 基带输入口不支持解包 `DST` 引擎私有的 `submode=6/7/8` 块压缩格式。

## 1. 协处理器固件真身举证：`bonobo.bin` 与 `dfe_app.bin` / `dfe_dat.bin`

### 1.1 `bonobo.bin`：Renesas H8S/2600 (H8SX) 机身防抖与机电控制 MCU
- **文件规模与头部结构**：`r3-310-decoded/bonobo.bin` 共 `172,144` (`0x2a070`) 字节。
  - `0x00000–0x0006f`：`7` 条 16 字节 Sony 分区段描述符（时间戳 BCD `11 0c 01 0a 17 29`、`10 09 05 ...`，目标段标识 `0x50, 0x52, 0x54, 0x56`）。
  - `0x00070–0x0016f`：标准 **Big-Endian 32-bit 异常与中断向量表**：
    - `Vector[0]` (`Reset`, `@0x70`) = `0x00000100`
    - `Vector[7]` (`NMI`, `@0x8c`) = `0x00010d3a`
    - `Vector[16..31]` (`IRQ/SCI/Timer`, `@0xb0..0x10c`) = `0x00010d3c`, `0x00010d6a`, `0x00010d6c`, `0x00010d82`...
  - 高频指令特征：`01 00 6d f6` (`stm.l (er6), @-sp`)、`01 00 6d 76` (`ldm.l @sp+, (er6)`)、`54 70` (`rts`)、`56 70` (`rte`)、`6a 28`/`6a a8` (`mov.b @aa:32, r0l`)，100% 吻合 **Renesas H8S/2600 / H8SX** 指令集。
- **与主固件 `AV-CAM.BIN` 的通信边界**：
  - `AV-CAM.BIN` 中的 `BonoboDSP_Send` / `BonoboDSP_Rcv` (`@0x2ad868–0x2ada20`) 使用固定 **`0x22` (34) 字节串口数据包**（首字节同步魔数 **`0x39`**，见 `@0x2ad884: cmp r3, #0x39` 与 `@0x2ad99e: movs r3, #0x39`），末尾附 16-bit 校验和 (`@0x73db38`)。
  - 相关日志字符串（`0x92fb00–0x930500`）全部指向 `Bear`（Sony 内部五轴传感器位移防抖 IBIS 代号）、快门、光圈及镜头卡口控制，与 ISP 图像管线完全隔离。

### 1.2 `dfe_app.bin` & `dfe_dat.bin`：传感器数字前端 (DFE) ARMv7 微码
- **架构与指令级特征**：
  - `dfe_app.bin` (`1,956` B)：`0x00–0x0f` 为 Little-Endian ARM32 到 Thumb-2 切换跳板（`000000ea` `b 0x8` -> `add r12, pc, #0x3b; bx r12` -> 进入 `@0x4a` Thumb-2 初始化入口）。`@0x10–0x48` 执行 `.data`/`.bss` 拷贝与清零，literal pool (`@0x58–0x78`) 指向 DFE 核心私有的片上紧耦合内存 **TCM/SRAM `0xfe1e0800–0xfe1f1000`**。
  - `dfe_dat.bin` (`65,536` B)：包含 4 个非空代码/数据段（`0x0000–0x4b50`、`0x4c00–0x5040`、`0x8000–0xc390`、`0xffe0–0x10000`）。起始 `0x00–0x1f` 为标准 ARM32 异常向量表（`e59ff018` `ldr pc, [pc, #0x18]`，IRQ 向量 `e51ff120` `ldr pc, [pc, #-0x120]` 对接硬件 VIC 中断控制器），向量目标位于 `0x01005000–0x0100c000`。
- **主固件加载与管线职责**：
  - `AV-CAM.BIN` 在 `SuperSlowManagerDfe` (`@0x1cbd00–0x1cc220`) 中通过资源 ID `0xf90437`、`0xf90438`、`0xf90439`、`0xf9043a` (`@0x1cbe54–0x1cbe60`) 读取固件并由 `@0x7089ee` 灌入 DFE。
  - `@0x1cbd44–0x1cc140` 的日志与参数校验（`'Initialize: invalid sensHDTim %d'`、`'DFE_INT0:Unknown port %d %d'`、`'SetParams: invalid rdcEncType %d'` `@0x1cc0b8`）证实：DFE 处于 **CMOS 传感器输入端 (`IIF`/`SGC`) 与 `CamCore` 之间**，仅处理 12/14-bit Bayer RAW 时序、相位对焦像素剥离与 RAW 域无损/轻损压缩 (`RDC`)，不参与 `CamCore` 之后的 YCbCr 图像缩放或 DCE 压缩。

## 2. `AV-CAM.BIN` 内存映射与全芯片 14 路 `RC`/`DST` 硅片引擎全景表

### 2.1 `static-view.o` 真实加载基址与 C++ RTTI 类层次
通过交叉核对 GOT 全局偏移表（起始于 `.text+0x011614f8`）、C++ RTTI `typeinfo` 结构体及虚函数表指针，确认 `static-view.o` 全段（长度 `0x0116c100`）运行时加载在单一平坦虚拟基址：
$$\text{Runtime VMA} = \text{0x635c6000} + \text{text\_offset}, \quad \text{File Offset} = \text{0x34} + \text{text\_offset}$$

## 3. `RC_IP_TYPE` 与 `submode` (`YcCompress`) 寄存器级语义解构

### 3.1 参数结构偏移与 `RC_IP_TYPE_IP` 真相
在 `WrapRcctResize` (`@0x6adda0–0x6adec6`) 构建并传入 `rcct_resize` (`@0x7944fc`) 的 `0xd0` 字节参数包中：
- **输入图像描述符**：
  - `[rcct + 0x4c]` = `in_color_format` (`0` = YCbCr 4:2:2 16bpp, `1` = YCbCr 4:2:0)
  - `[rcct + 0x50]` = `in_submode` (`YcCompress` 子模式)
  - `[rcct + 0x54]` = `in_ip_type` (`0`/`1` = DRAM 内存帧缓冲, **`2` = `RC_IP_TYPE_IP` 片上 IP 直连/eSRAM VMC**)
- **输出图像描述符**：
  - `[rcct + 0x98]` = `out_color_format`
  - `[rcct + 0x9c]` = `out_submode` (`YcCompress` 子模式)
  - `[rcct + 0xa0]` = `out_ip_type` (`0`/`1` = DRAM 内存帧缓冲, **`2` = `RC_IP_TYPE_IP` 片上 IP 直连/eSRAM VMC**)

`RcResizeDst::CheckInputImage` (`@0x4670b8`) 在 `[calc + 0x5c] != 2` 时检查 DRAM 地址 8 字节对齐，失败时打印 `@0x4670f6` **`"Not RC_IP_TYPE_IP: 8byte alignment\n"`**，直接铁证 `ip_type == 2` 代表无 DRAM 地址的片上硬化流水线直连。前期在 `Sequence_Movie` (`@0x3632e8`) 观察到的 `#2` 正是 `ip_type = 2`，而非 `YcCompress = 2`。

### 3.2 `submode` 各枚举值的硬件校验与寄存器编码差异
对比 `RcResize` 与 `RcResizeDst` 的校验器及寄存器计算器，可精确还原全部 `submode` 硬件语义：

1. **`submode = 0`**：未压缩 8-bit YCbCr（`RcCalc` `@0x7953e6` / `@0x795918`）。
2. **`submode = 1`**：**标准 8-bit DCE 块压缩 (`YcComp`)**：
   - 输入校验 `RcResize::CheckInputImageType` (`@0x46a0e8`)：要求 `(caps & 0x100) != 0`。
   - 输出校验 `RcResize::CheckOutputImageType` (`@0x468e28`)：要求 `(caps & 0x200) != 0`。
   - 对齐要求：`CheckOutputImageMirrorYcCompAlignment` (`@0x46b344`) 与 `CheckOutputImageMirrorYcCompStripWidth` (`@0x46b3ec`) 强制要求 **64 像素对齐** (`tst r3, #0x3f`)。
3. **`submode = 2, 3`**：无压缩分块/Tile 寻址模式（`@0x7957a4`、`@0x795808`）。
4. **`submode = 6` 与 `submode = 7, 8`（仅存在于 `DST` 引擎 `RcResizeDst::CalcRegister` `@0x467b34`）**：
   - **普通 `RCH`/`RCV` (`0xf3880000` / `0xf3980000`) 完全不支持**：其 `RcResize::CalcRegister` (`@0x794f9e` / `@0x7952e6`) 根本不调用 `@0x79476c`/`@0x794792`，遇到非 `{0,1,2,3}` 的 `submode` 不会生成任何有效压缩控制字。
   - **`DST` 引擎 (`0xf3500000`) 专属处理**：
     - 在 `RcResizeDst::CheckOutputImageType` (`@0x4673e0`) 中：`subs r3, #7; cmp r3, #1` 专门拦截 **`submode == 7` 或 `8`**，强制校验 **`(caps & 0x800) != 0`**，并在 `@0x45a460` / `@0x794d34` 采用 **32 像素条带对齐**（对应 16-bit/10-bit 扩展位宽下每块 64B 容纳 32 像素，区别于 8-bit `submode=1` 每块 64B 容纳 64 像素）。
     - 在 `RcCalcDst` `@0x79476c` (输入) 与 `@0x794792` (输出) 中：
       - `submode = 6` -> `mode = 2, ext_10bit_flag = 0`；
       - `submode = 7` -> `mode = 1, ext_10bit_flag = 1`；
       - `submode = 8` -> `mode = 2, ext_10bit_flag = 1`。
   - **软件包装层封锁**：前期在离线拍照路径见到的 `@0x6ab3ca` (`submode=6`) 仅服务于非实时 `ApiRc` (`WrapRcSub1`)；而实时流式 `WrapRcctResize` (`@0x6ade0a`/`@0x6ade58`) 与 `WrapRcctDistCorrection` (`@0x6ad98e`/`@0x6ad9d0`) 均调用 `WrapRcBase::SetYcCompress` (`@0x120a7c`)，该函数在 `cmp r5, #5; bhi 0x120aac` 处直接拒绝所有 `> 5` 的输入并抛出 `[SDF][INT_ERROR] SetYcCompress`。

## 4. 实时视频全链路位深审计（`APL` -> `RCH/RCV/DST` -> `Spica/VFX` -> `Imola VCD`）

沿着 α7R III 实时视频录制数据流向逐级核查，可见整条后端 YCbCr 管线被严格锁定在 **8-bit** 平面：

```
[CMOS 14/12-bit RAW]
       │ (SLVS-EC)
       ▼
[DFE (dfe_app/dat @ 0xfe1e0000)] ──► 仅做 HD/VD 同步、ZPD1 相位对焦剥离、RAW RDC 压缩
       │ (Bayer RAW)
       ▼
[CamCore ISP] ──► Demosaic + 3D LUT / S-Log2 / S-Log3 / HLG 曲线映射 ──► 量化为 8-bit YCbCr 4:2:2
       │
       ▼
[APL Movie (apl_mov_set_aic @ 0x375e74)] ──► W0/W1/R2(eSRAM) 输出 8-bit YCbCr
       │
       ├──(无畸变校正: EXEC[5..10] RCH/RCV @ 0xf3880000/0xf3980000, caps&0x800==0, 仅 8-bit)
       └──(开畸变校正: EXEC[12..13] DstH/DstV @ 0xf3500000, 主干走 ip_type=2 片上直连)
       │
       ▼
[Spica EIS (@0x46d844) / VFX (vfx_4k_movie_prm_gen @ 0x16c02c)] ──► 8-bit 步幅计算 + SyncYCOut (HDMI 8-bit 4:2:2)
       │ (DRAM 8-bit YCbCr 4:2:0 帧缓冲)
       ▼
[Imola VCD (vcd_firmware.bin + ENCHANDLER @ 0x41243a)] ──► 硬编码 CodecType=1 (AVC), BitDepth=0 (8-bit), ChromaFormat=1 (4:2:0)
```

### 4.1 后端硬件编码器 `Imola VCD` (`vcd_firmware.bin` + `ENCHANDLER`) 的决定性铁证
1. **硅片微码层 (`r3-310-decoded/vcd_firmware.bin`, `5,445,340` B)**：
   - 版本字符串 `'SW_VER_12_21_31_0'`，构建路径 `'/cygdrive/c/UCP/ReleaseBuild/tags/Astra/20171004_12_21_31_0/Src/Release/Ucp/Vcd/Spu/build'`，揭示 α7R III 主控 BIONZ X 芯片内部代号为 **"Astra"**，视频编解码硬件 IP 代号为 **"Imola"**。
   - 固件内同时编译了 `AVC`、`HEVC` (`venc_ctrl_hevc.cxx`) 与 `MPEG2` 控制栈，并在公共校验中保留了断言 `'bit_depth <= VdoBitDepth_10bit'`（与同平台 HEIF/HLG 10-bit 静态图像硬件能力同源）。
   - VCD 内部参考帧压缩使用的是其独立的 **EBC (Embedded Block Compression, `EbcModeLD` / `EbcModeCD`)**，与 ISP 侧 `RC`/`DST` 的 `DCE` 块压缩并非同一套内存格式。
2. **主固件驱动与通道配置层 (`AV-CAM.BIN` `CMNHANDLER` `@0x4061bc` & `ENCHANDLER` `@0x40b300` / `@0x4122d8`)**：
   - 视频录制通道创建函数 `@0x41243a–0x412550` 组装 `ImolaCreateCh` 参数包（`@0x406200–0x406410` 打印 `[CMNHANDLER]Hsize / Vsize / BitDepth / ChromaFormat / CodecType`）并调用 `@0x4061bc`。
   - 位于 `.data` 段 `@0x1125d68` 的 4K UHD 默认通道规格表为：
     `Hsize = 0x0f00 (3840)`, `Vsize = 0x0870 (2160)`, **`BitDepth = 0x0` (8-bit)**, **`ChromaFormat = 0x1` (4:2:0)**。
   - 编码器启动配置 `ENCHANDLER` (`@0x40b42e: cmp.w r8, #0x1; bne.w 0x40bbfe`) 仅对 `CodecType == 1` (H.264/AVC) 填充完整视频编码参数（`[r5, #0x16]` `Profile`、`[r5, #0x18]` `ChromaFormat`、`[r5, #0x19]` `BitDepth`），整套 α7R III 视频状态机、码率控制及 XAVC S 封装器均不存在 10-bit H.264 High 10 或 10-bit HEVC 视频录制通路。
